# Android

OpenRAC runs on Android phones, tablets and handhelds with:

- a 64-bit ARM CPU (arm64-v8a),
- Android 10 (API 29) or newer,
- a Mali or Adreno GPU with OpenGL ES 3.2.

There is no emulation. The APK holds the same translated game code as the
desktop build, compiled with the Android NDK, and the game data comes from
your own disc. This page explains how the Android version works; building
and device tests are in [port/android/README.md](../../port/android/README.md).

## At a glance

- One APK holds the launcher and the game.
- The launcher is the desktop launcher (Tauri 2 + Svelte), so it works the
  same.
- The game runs as its own Android activity, in its own process.
- You pick a disc image once and the launcher sets the game up on the
  device. Everything lives in the app's storage, which the Files app shows
  as OpenRAC.
- A controller works everywhere; touch controls appear when you touch the
  screen.
- The launcher updates itself from GitHub releases.
- The game draws with OpenGL ES by default. A Vulkan renderer can use a
  custom Adreno driver (Turnip).

## One APK, two parts

**The launcher** is the desktop launcher's interface and logic
(`launcher/core`), built with Tauri 2's Android support. Its Android project,
`launcher/src-tauri/gen/android`, is generated by `tauri android init` and
committed. The library, game pages, settings, saves and mods behave as on the
desktop, and it always plays from the copy of OpenRAC inside the APK.

What only Android can do (the system file picker, importing a disc or a
driver, starting the game) goes through a small Kotlin plugin,
`OpenracPlugin`. Where a desktop command does the same job, it has the same
name and arguments.

Tauri was chosen so that there is one interface for every platform: the
launcher's Rust compiles for Android unchanged. A native Kotlin launcher would
be smaller, but it would be a second launcher to keep in step.

**The game** is `GameActivity`: SDL3's `SDLActivity` loading the game as a
library (`libopenrac-rac1-pal.so`, whose `main` SDL calls as `SDL_main`). It
runs in its own process (`:game`), because it reserves 4 GB of address space
and quits with `exit()`, and in its own task, so the game and the launcher
are two windows in Recents. While the game runs, its page in the launcher
offers *Return to game* and *Stop the game*.

## Building and running the game

- **Build.** `cmake --preset android-arm64` cross-compiles the port with the
  NDK; hostgen still runs on the build machine. The game becomes a shared
  library and SDL3 `libSDL3.so`. `tools/build_android.py` copies both into
  the launcher's `jniLibs/arm64-v8a`. The preset links with ThinLTO
  (`OPENRAC_PORT_LTO`).
- **Graphics.** The renderer targets desktop OpenGL 4.1 and asks for an
  OpenGL ES 3.2 context on Android:
  - the two missing functions (`glClearDepth`, `glPolygonMode`) are replaced
    in `renderer/gl.cpp`;
  - shaders are written in GLSL 4.10 and turned into GLSL ES 3.20
    (`es_source` in `renderer/shader.cpp`);
  - without `GL_NV_shader_noperspective_interpolation` some values are
    interpolated with perspective, and without `GL_EXT_clip_cull_distance`
    the 2D layer's widescreen crop is skipped;
  - `OPENRAC_GL_API=es` runs the same path on a desktop, which is how CI
    tests it on Mesa.
- **Files.** The launcher passes every path on the command line and in the
  environment (`--data`, `--levels`, `HOME`, `XDG_DATA_HOME`), so `main.cpp`
  has no Android paths.
- **Older Android.** bionic has `backtrace()` only from Android 13 (API 33);
  Android 10 to 12 use a replacement built on `_Unwind_Backtrace`
  (`port/android/compat`). `memfd_create` goes through `syscall` below
  API 30.
- **Refresh rate.** The game asks for the display's fastest rate while it is
  in front (`GameActivity.java`), or a 120 Hz panel can drop to 60 Hz and
  stay there.

## Controls

Controllers work as on the desktop: Bluetooth, USB and handhelds' built-in
pads. A round stick is stretched near its rim to the DualShock 2's square, so
a full diagonal runs; a stick that already reports a square is left as it is
(`platform/pad.h`).

The on-screen pad (`platform/touch_pad.h`, drawn by one shader in
`renderer/ui/touch_overlay.cpp`):

- appears when you touch the screen, and hides when you use a controller or
  leave the screen alone for ten seconds;
- is laid out from the screen edges inside the safe area, with the shoulder
  buttons clear of the health and bolt counters. A test checks that no
  controls overlap at the usual screen shapes and sizes;
- has a left stick that moves to wherever your thumb lands;
- has no visible right stick. A finger on the right of the screen, away from
  the buttons, holds an invisible stick centred where it landed. The camera
  turns while it is pushed (full speed at `kLookReach`), and pushed further
  the centre follows the finger;
- can be resized and moved from the drawer (below).

## Where your files are

The app keeps everything in its own storage (`files/`): the games
(`files/games`, the install folder), saves and settings
(`files/share/openrac`), disc images, GPU drivers and screenshots.

- The Files app shows them in its sidebar as OpenRAC, with the free space, as
  Dolphin and Eden do (`FilesProvider.kt`, authority `<package>.files`).
  Settings has an Open Files button.
- `hasFragileUserData` makes uninstalling ask whether to keep the data; it
  comes back when the same app, signed with the same key, is reinstalled.
- An older install (shared storage's `OpenRAC`, or the app's data folder) is
  moved into `files/games` at the first start (`install::settle_games_dir`),
  and the first-run folder screen is skipped.

## Setting up a game

**The disc.** Android's picker hands over an open file, not a path, and the
game reads the disc for as long as it runs, so the image is copied once into
`files/discs/`, after a free-space check and with progress shown. A `.chd`
image (from `chdman createdvd`) is unpacked to `.iso` instead
(`launcher/core/src/chd.rs`).

**The setup** is the desktop's: `tools/extractor.py`, `editor/extract.py port`
for the levels, then the game's `--check-levels`, with their output in the
launcher. Android runs programs only from an app's native library folder, so
the APK carries them as libraries:

| Library | What it is |
|---|---|
| `libpython3.13.so`, `libopenrac-python.so` | CPython for Android from [Chaquopy](https://github.com/chaquo/chaquopy) (MIT, pinned from Maven Central), and a small `python3` around it (`port/android/python_main.c`) |
| `libopenrac-<id>-cli.so` | the game without a window, for `--check-levels` |
| `libopenrac-probe-bake.so` | Enhanced graphics' probe baker, with Embree built by the NDK (the release `tools/build_port.py` pins) |

The copy of OpenRAC (`tools/bundle_standalone.py --android`) is
`assets/openrac.zip`. When the APK changes, `OpenracSetup.kt` unpacks it into
`files/openrac.new`, swaps it for `files/openrac`, and links `python3` and the
game's programs to the libraries above. The launcher waits for this, and says
so if it takes more than a second.

**Kept light for a phone:**

- the image is copied by the kernel (`copy_file_range` or `sendfile`);
- the extractor writes only `SYSTEM.CNF` and the boot executable
  (`--boot-only`), though it still checks every file;
- Android's Python has no process pools (no `sem_open`), so `editor/extract.py`
  runs up to four levels in separate processes (`SubprocessPool`);
- the enhanced lighting bake lets each baker use every thread and starts the
  largest levels first, so the last one does not bake alone on one core
  (`bake_all.py`). The result is the same at any thread count.

You can leave the app during setup: a foreground service (`SetupService.kt`)
keeps it going and shows the step in a notification (`backgroundStatus` in
`launcher/src/lib/progress.ts`).

**Playing** runs no program: the launcher starts the game's activity with the
desktop's command line and the Play action's environment. With Enhanced
graphics on, that adds the Vulkan renderer and the baked probes (`--probes`).
Nothing leaves the device.

## The launcher on Android

The launcher is full screen; swipe to show the system bars, and the page
keeps clear of a camera cut-out (`MainActivity.kt`). A controller drives it
(`launcher/src/lib/pad.ts`, the Gamepad API on a desktop):

| Button | Does |
|---|---|
| D-pad or left stick | moves the focus in that direction |
| A | presses |
| B | closes a menu or dialog, then goes back to the games |
| LB / RB | switch tabs |
| Back | as B; from the games list it leaves the launcher (a running setup goes on) |

The pages are arranged for a handheld, with a navigation rail:

- Games has a compact card per game. The last one picked is ringed, and the
  launcher takes its colour: Ratchet & Clank orange, Going Commando light
  blue, Up Your Arsenal yellow, Deadlocked red, Size Matters blue
  (`launcher/src/lib/themes.ts`).
- Mods and Develop work on the game picked on Games, named at the top right.
- A game's page keeps Play and the saves at hand; Differences from the
  original and Help (logs and crash reports) are folded.
- Pages slide in the rail's order (a view transition). With reduced motion
  they simply change.

## The in-game drawer

The desktop's menus (View, Graphics, Sound, Developer) are a drawer on
Android, as in an emulator. It slides in from the left over the paused game
with the pad's options button, Back, or a controller's Guide button.

Its rows sit on cards like the launcher's settings, big enough for a thumb,
and a controller moves through them (left and right change a value, B
closes). It wears the launcher's theme and the game's accent, which the
launcher passes at Play (`OPENRAC_UI_COLORS`), and moves with the launcher's
easing. The cards:

- **Graphics:** picture shape (4:3 to 32:9, or the whole screen), HUD
  position, render scale, anti-aliasing, texture filtering, frame rate, VSync
  and the FPS counter.
- **Enhanced graphics** (when on in the launcher's Mods): its switch, modern
  shadows, bounced light and its strength, ambient occlusion and its quality.
  When this run cannot have it, the card says why.
- **Sound and game:** volume and skipping cutscenes.
- **Touch controls:** button size, camera speed and *Move the controls*:
  drag them over the paused game, with a bar to resize, reset and finish. A dragged group snaps to a nearby line (its own place, the
  middle, another group or its mirror image), and the line is shown.
- **Developer tools**, folded: the debug overlay, pause, a frame step, game
  speed, a screenshot (to `files/screenshots`) and, in developer mode, the
  level select.
- **Quit.**

Changes are saved and applied at once. Back, Resume, B or a touch outside
closes it. The code is in `port/game/common/debug/drawer.cpp`;
`OPENRAC_DRAWER=1` shows it on a desktop. The debug overlay scrolls with a
finger, and a controller moves through it while the game is paused.

## Updating the launcher

Android does not let Tauri's updater replace the app in place, so the
launcher has its own, with the same manifest (`latest.json`, whose
`android-aarch64` entry is the APK) and signing key:

1. It downloads the APK into its cache.
2. It checks the signature against the public key in `tauri.conf.json`
   (`launcher/core/src/update.rs`).
3. It hands the APK to `PackageInstaller`. Android asks you to confirm, and
   checks the new APK has the installed one's Android key.

The first time, Android asks to let the launcher install apps. If you left
the launcher meanwhile, the confirmation waits in a notification
(`UpdateReceiver.kt`). Only a build with the launcher's own Android key is
updated or offered as an update, so Android never refuses one. Releases are
signed with it ([RELEASING.md](../../launcher/docs/RELEASING.md)).

## GPU drivers

The kinds of driver Android emulators (Skyline, Yuzu's successors, Eden,
Citron, Winlator Bionic) use, and what they mean here:

| Driver | GPUs | How you get it | In OpenRAC |
|---|---|---|---|
| The system's OpenGL ES driver | Mali, Adreno | every app has it | the default |
| An updated system driver | the vendor's | Android's updatable graphics drivers | works as is |
| ANGLE (OpenGL ES on Vulkan) | both | Developer options, "ANGLE preferences" | works as is; helps where the GLES driver is broken |
| A custom Vulkan driver (Mesa Turnip, newer Qualcomm drivers) | Adreno | a zip with a `meta.json` (`name`, `author`, `vendor`, `driverVersion`, `minApi`, `libraryName`: Eden's format), loaded by [libadrenotools](https://github.com/bylaws/libadrenotools) (BSD-2-Clause) | needs the Vulkan renderer |

Custom drivers work only with Vulkan: libadrenotools hooks the Vulkan loader,
nothing does that for OpenGL ES, and ANGLE cannot use another Vulkan driver
without patching. Mali has no replacement drivers worth loading (Eden offers
them only where `/dev/kgsl-3d0` exists), so there the choices are the first
three rows. The custom-driver
path has three parts:

1. **Packages** (`OpenracPlugin.kt`, "GPU driver" in Settings). An imported
   zip's `meta.json` is checked (`libraryName` must be in the zip, `minApi`
   not above the device's), and it is unpacked into
   `files/gpu_drivers/<id>/`. The chosen one reaches the game in
   `OPENRAC_GPU_DRIVER_DIR` and `OPENRAC_GPU_DRIVER_LIBRARY`.
2. **Loading** (`port/android/gpu_driver.cpp`). On Adreno the game opens it
   with `adrenotools_open_libvulkan`, and logs the driver's name and version
   or why it was refused. Elsewhere, or on failure, the system driver is used.
3. **The Vulkan renderer** (`port/renderer/vulkan/`) carries out the small
   set of OpenGL calls the renderers use (`renderer/gl.h`,
   `renderer/world/gl_world.h`) on Vulkan 1.3: shaders through glslang,
   pipelines cached by state, buffers streamed through a per-frame ring.
   "Renderer" in Settings selects it (`OPENRAC_GL_API=vulkan`); if Vulkan 1.3
   cannot start, the game falls back to OpenGL ES.

**Decided:** the Vulkan renderer stays a translation layer, measured before
any part becomes native Vulkan. `--debug-dump` writes its numbers per frame
(`vk_*`: draws, pipelines made, ring use, flushes, CPU time drawing,
presenting and waiting), and the costliest paths are rewritten first. A
patched ANGLE was considered and not chosen. The drawing tests also run on
Vulkan (`*_vulkan`, with validation, on Mesa's lavapipe in CI).

**Why Vulkan and custom drivers gain less here than in an emulator.** An
emulator is held back by the GPU, drawing the console's picture at several
times its size. The port draws a PS2 game natively, which a current Adreno
does with time to spare, so the frame waits on the CPU: the game's code and
the renderer's calls. A better driver changes neither; ThinLTO helps both
renderers. `OPENRAC_FRAME_COST` (`scene`, `submit`, `gpu`, `show`) and the
`vk_*` numbers show where a device's frame goes.

## Building and CI

`tools/build_android.py` builds everything: Python, the port with the NDK,
the libraries and SDL's Java code into the launcher's Android project, the
copy of OpenRAC, and the APK (`yarn tauri android build`).

In CI (`.github/workflows/launcher.yml`) Android is a row of the build matrix
on `ubuntu-latest`, which has the SDK and NDK: `build_android.py --no-apk`,
then the APK, kept with the other installers and added to the draft release
on a `launcher-v*` tag. `checks.yml` runs the port's OpenGL ES tests on Mesa
and the Android launcher pages in a headless browser (`yarn test:android`).

**Signing.** With the repository's `ANDROID_KEYSTORE` secrets the APK has the
launcher's key; without them a throwaway debug key, so each build installs
fresh. `python3 tools/android_keystore.py` makes the key and prints the
secrets ([RELEASING.md](../../launcher/docs/RELEASING.md)).

**Forks.** Outside `OpenRAC/OpenRAC` CI builds a separate app that installs
beside the project's, with its own data: package
`dev.openrac.launcher.fork_<owner>`, named "OpenRAC Fork", file
`OpenRAC.Launcher.Fork_<version>_android-arm64-debug.apk`
(`OPENRAC_ANDROID_APPLICATION_ID`, `OPENRAC_ANDROID_APP_LABEL` in
`app/build.gradle.kts`). The project's builds and pull requests keep
`dev.openrac.launcher`.

## Tested by hand

CI has no phone and no disc, so these are checked on a device
([port/android/README.md](../../port/android/README.md)): the launcher's
screens, importing a disc, the first frames on Mali and Adreno, a controller
and the touch pad, the drawer, suspend and resume, the Vulkan renderer and its
fallback, and on Adreno a Turnip package loading and drawing.

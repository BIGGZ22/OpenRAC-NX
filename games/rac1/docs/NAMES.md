# Names

Every symbol keeps its address name: `func_<ADDR>` in the executable,
`func_LNN_<ADDR>` in level code, `D_<ADDR>` / `D_LNN_<ADDR>` for data.
The build and every tool read the address (and level) out of that name
(DECOMP_PROGRESS.md, "Real function names"), so it is what C declares and
defines, what `INCLUDE_ASM` names and what the linker sees.

Readable names sit on top, as macros:

| File | What it is |
|---|---|
| `config/names.tsv` | the table: one row per named symbol, its name, tier, source and the evidence that put the name on this PAL address |
| `include/names.h` | generated from the table: `#define FadeToBlack func_001F4E08`, for every name not a candidate; included by `common.h` |
| `tools/names.py` | `build` (sources to table), `header` (table to names.h), `apply` (bodies use the names), `check`, `ntsc` and `rename` (below), and lookup: `python3 tools/names.py func_001F4E08` or `... FadeToBlack` |
| `config/names_ntsc.tsv` | generated by `tools/names.py ntsc`: every name of the NTSC decomp placed exactly on one of our symbols, with what became of it |
| `config/modules.tsv` | generated by `tools/names.py ntsc`: the NTSC decomp's source file for each of our functions (metadata only) |

C writes the readable name in function definitions and inside function
bodies, and the address name everywhere else (declarations and prototypes,
`__asm__` labels, `_r` definitions, comments that cite a symbol). The
preprocessor turns one into the other, so the objects are byte for byte
the same either way. Tools that find definitions by address read source
through `tools/srcnames.py`, which maps readable names back.
`tools/names.py apply-defs` renames definitions, `apply` renames uses in
bodies. `tools/dossier.py` shows a function's name in its `CONTEXT.md`.

Core/SDK/libc functions (`src/core`) are in the table but not in the
header: their names (`memcpy`, `sceGsSync`, `rand` ...) are the libraries'
own, and a macro for them would shadow the real library spelling.

## Tiers

| Tier | In names.h | Meaning |
|---|---|---|
| recovered | yes | the original identifier: `config/symbol_names.txt`; the NTSC decomp's `symbols.txt` as it stood before its 2026-09 automated naming loop; a symbol Lombyte recovered |
| descriptive | yes | a later name with evidence: the NTSC decomp's 2026-09 names, a Lombyte proposal of high confidence, a ReRAC name marked verified, the PAL memory map (globals) |
| candidate | no | weaker: Lombyte medium confidence, ReRAC suggested or inferred, or a name another symbol already took. Shown in dossiers for workers |

The NTSC decomp's names (below) come on top of these: they replace every
name that is not recovered.

When sources disagree, the best tier wins, then the source order above;
the other names are kept in the `alternatives` column. A name is given to
one symbol only.

## Local names

`config/names_local.tsv` holds names this project gives from reading the
code (`symbol`, `name`, `evidence`, optional `override`). `tools/names.py
local` merges it into `names.tsv` (and `build` applies it too): a local name
fills a symbol with no name or only a candidate, as tier descriptive;
`override` replaces a wrong recovered/descriptive name, keeping the old one
in the alternatives. After `local`, run `header`, then `apply-defs` and
`apply`.

## The NTSC decomp's names

We are converging on the NTSC decomp's conventions (Lombyte's project, read
at the commit pinned in `config/versions/us/ntsc_decomp.txt`), so its spelling wins: its names, snake_case as
it writes them, replace every name of ours that came from reading the code
(`names_local.tsv`) or from another later source. A recovered name, the
original identifier, is never replaced.

```sh
python3 tools/names.py ntsc     # read the pinned NTSC decomp; write names_ntsc.tsv, modules.tsv, names.tsv
python3 tools/names.py rename   # carry the changes into names.h and src/
```

`python3 tools/ntsc_source.py follow` bumps the pin and runs both, so the
names follow the pinned commit; nothing of its code is copied. The NTSC
decomp is read from a cache outside the checkout
(`~/.cache/rac1-decomp/ntsc/<commit>`, a shallow fetch of that one commit;
`RAC1_NTSC_DECOMP_DIR` points at a checkout of your own instead). `ntsc` reads
the names its C binds to US addresses with asm labels
(`void f(void) __asm__("FUN_001f5f18")`, `extern s32 x __asm__("D_0015EE98")`)
and the C files its splat config names after their function, then places
each on our symbol:

- a function through `config/versions/us/functions.tsv`: the US function
  at that place and its PAL counterpart;
- a datum through the US translation table of `tools/version_check.py`,
  only where code of both versions refers to exactly that address. Data
  placed only approximately are skipped.

Each placed name gets a status in `config/names_ntsc.tsv`:

| Status | Meaning |
|---|---|
| adopted | the symbol's name now (tier descriptive, source "the NTSC decomp"); the name it replaces goes to the alternatives |
| same | our name already |
| kept-original | our name is recovered and stays; theirs goes to the alternatives |
| held-alias | one of the symbol's places goes by several names in the NTSC decomp |
| held-several-symbols | the name lands on more than one of our symbols |
| held-several-names | the symbol gets more than one name |
| held-clash | another symbol keeps that name |
| held-unreferenced | a datum nothing of ours refers to |
| held-library | a core/SDK/libc function: it keeps its library's own name |

Held names are candidates: listed as alternatives, or as a candidate row
where the symbol has no name. The table records the row an adopted name
replaced, so `ntsc` gives the same result run after run, and `local` keeps
the NTSC decomp's names on top of local ones.

`rename` turns every use of a name names.h no longer gives that symbol back
into the address name (the new spelling in comments), then runs `header`,
`apply-defs` and `apply`. A name that is already another identifier in
`src/` or `include/` (a struct field, a label) stays out of names.h, as
before.

## Sources (all RaC1)

- **NTSC decomp**: matching NTSC
  decompilation; `config/symbols.txt`, mangled GCC 2.x names demangled to
  the base name (`Class_method` for members).
- **Lombyte** (github.com/mateuszklysz/Lombyte, MIT): matching US
  decompilation; `config/us/recovered_names.json` and its report.
- **ReRAC** (github.com/re-rac/rerac, ISC): native PC port;
  `tools/ghidra/names/doc_names.csv`, the names its design docs give to
  US boot and level functions after reading them in Ghidra.
- **PAL memory map**: the community spreadsheet "Ratchet & Clank Series
  Addresses" (RaC1 sheet, PS2 PAL column). Only addresses that are the
  exact start of one of our `D_` symbols, with accesses of the described
  size, are used (the list is `MEMORY_MAP` in `tools/names.py`).

## From US addresses to PAL symbols

- **Executable:** function-size alignment of the US executable (Lombyte's
  report) against ours, runs of four or more equal sizes, as
  `tools/lombyte.py` does. Lombyte's report gives ROM offsets, converted
  with its splat segment's `start`/`vram`.
- **Level code:** Lombyte's US overlay catalogue
  (`config/overlays/us/functions.tsv`) fingerprints functions exactly as
  `tools/overlays.py` does. 3,828 of our 4,040 fingerprints occur once in
  each catalogue; with the same size, that is the same function, and its
  US places map to our catalogue name. The same pairs cover the
  executable functions the levels hold (`exe` kind).
- **Cross-checks:** where alignment and fingerprints both place an
  executable function they must agree (they do everywhere; a
  disagreement would drop both). Of the functions `symbol_names.txt`
  already named, the NTSC decomp's and Lombyte's names placed by the alignment agree
  209 of 209.

## Refreshing

```sh
NTSC=... LOMBYTE=... RERAC=... python3 tools/names.py build
python3 tools/names.py header
python3 tools/names.py apply      # new C that still spells address names
python3 tools/names.py apply-defs # definitions by their readable names
python3 tools/names.py check
```

`build` needs full clones (the NTSC decomp's history dates its names). Then rebuild
and check that nothing but source text changed.

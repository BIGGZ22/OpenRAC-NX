# Data structures

Vectors, `Moby`/`MobyClass`, the hero, the pad, and the main globals.
Moby behaviour is on [mobys.md](mobys.md). A port must keep these layouts
exactly.

Reading the tables:

- Offsets are generated by clang from `include/*.h`
  (`build-sn/tidy/`, `conv.canon_layouts`). The headers win over this page.
- Only named fields are listed; gaps are unused `pad_*` bytes. `unkXXX` =
  accessed, meaning unknown.
- Notes come from header comments. `FUN_Lxx_...` / lowercase names there
  are NTSC-decomp (US) labels; see [Addresses](#addresses-pal-vs-us).

## Vectors (`include/vector.h`)

| Type | Size / align | Layout | Use |
|---|---|---|---|
| `Vec4f` | 16 / 4 | `f32 x, y, z, w` | A float vector embedded in records whose alignment is only 4. `Moby.pos`, `Moby.rot` and `Moby.bsphere` use it. |
| `Vec4A` | 16 / 16 | `f32 x, y, z, w`, `aligned(16)` | The same four floats, aligned so that one `lq`/`sq` moves them. |
| `VecQuad` | 16 / 16 | `u32 __attribute__((mode(TI)))`, a 128-bit integer | The raw quadword. It isn't called `u128` because source files declare their own `u128`. |
| `Vec4` | 16 / 16 | `union { VecQuad q; f32 f[4]; s32 i[4]; }` | The general 16-byte vector: copy it as one quadword (`.q`), read it as floats (`.f`), or zero/test it as ints (`.i`). The hero and its sub-records use it everywhere. |

Alignment:

- `lq`/`sq` (and `qcopy`/`qzero`) ignore the low four address bits. A
  misaligned `Vec4` does not fault; the access silently rounds down to the
  containing quadword.
- A port must keep `Vec4`/`Vec4A` 16-aligned and 16 bytes long. A 4-aligned
  `struct {float x,y,z,w;}` is only right where retail used `Vec4f`.
- `Vec4f` vs `Vec4` changes codegen (struct padding, whether gcc uses
  `lq`), so both exist.

### Moby.flags (0x34) bits known from code

| Bit | Meaning | Evidence |
|---|---|---|

| 0x0010 | has a glow colour (class +0x40 copied to `glow_color`) | `InitMobyInstance` |

| 0x0400 | class has a shadow (class byte +0x0F); `shadow_range` set to 0x18 | `InitMobyInstance` |

### Button bits

From the first two report bytes (`func_002181F0_r`):

```c
p->raw_held = p->held = ((buf[0] << 8) | buf[1]) ^ 0xFFFF;   /* active-low -> active-high */
```

| Bit | Button | Bit | Button |
|---|---|---|---|
| 0x0001 | L2 | 0x0100 | Select |
| 0x0002 | R2 | 0x0200 | L3 |
| 0x0004 | L1 | 0x0400 | R3 |
| 0x0008 | R1 | 0x0800 | Start |
| 0x0010 | Triangle | 0x1000 | Up |
| 0x0020 | Circle | 0x2000 | Right |
| 0x0040 | Cross | 0x4000 | Down |
| 0x0080 | Square | 0x8000 | Left |
| 0x10000 | *synthetic*: stick flick (only in `pressed`, see below) | | |

Confidence: **high for the d-pad bits, inferred for the rest.** No source
names the buttons; the table is the standard PS2 digital report, and the
code agrees wherever checkable:

- Left stick: x < 0 ORs 0x8000, x > 0 0x2000, y < 0 0x1000, y > 0 0x4000
  (y is negative up). `no_direction` tests `held & 0xF000`.
- Mirror swaps exactly 0x8000/0x2000. `mode` 2 keeps only 0x900
  (Start|Select).
- Commonest gameplay test: `pressed & 0x40` (69 sites; Cross = jump), then
  0x10, 0x20. Weapon swap tests 0x10 (Triangle) in `raw_released`.
- Menus close on `pressed_unmasked & 0xD00` (Start|R3|Select) when not
  locked (`src/overlays/shared/pause_00277208.c:688`). The header calls
  0xD00 "accept"; the call sites read as "close menu" (likely).

### The held/pressed/released family

Set by `func_002181F0` once per poll:

| Field | Meaning |
|---|---|
| `raw_held` | buttons only (after the mirror swap, before stick directions). `mode` 2 masks it. |
| `held` | `raw_held` plus the left-stick directions as d-pad bits (0x8000/0x2000/0x1000/0x4000) |
| `prev_held` | `held` of the previous poll. UpdatePad restores it from the latch `unk348` before polling. |
| `pressed` | `~prev_held & held`. Plus 0x10000 on a stick flick, and overwritten by key repeat. Forced to 0 while `unk18C != 0` (on pad 0 at `D_0013CA40`). |
| `released` | `~held & prev_held`. Forced to 0 like `pressed`. |
| `raw_pressed` / `raw_released` | `~prev_held & raw_held` / `~held & prev_raw_held`. As retail has it, these mix the raw and stick-augmented masks. Do not "fix" that. |
| `held_unmasked`, `pressed_unmasked`, `released_unmasked` | copies taken **before** the `mode` masks, with the mirror swap undone (so menus see the physical left/right). Menus read these. |
| `no_buttons` | `held == 0` |
| `no_direction` | `(held & 0xF000) == 0` |
| `stick_moved` | `analog[2]` or `analog[3]` nonzero |
| `mode` | one-shot input lock, reset to 0 after it is applied. 1 clears 0x5030 (Up, Down, Triangle, Circle) from held/pressed/released and zeroes `analog[0..1]`. 2 keeps only 0x900 in held/pressed/released/raw_held, sets `no_direction` and zeroes `analog[2..3]`. |

`ClearPadInput` (`func_00218188`) zeroes the current masks (not
`prev_held`/`prev_raw_held`/`mode`), `stick_moved` and both analog arrays,
and sets `no_buttons = no_direction = 1`. Runs while the device is not
ready or its profile is being read.

### Analog values

- `analog[0..3]`: report bytes 2..5, centred on 0x7F, dead zone 0x30,
  scaled `(d - 0x30) / 0x4C`, clamped to 1, signed. Needs a report >= 6
  bytes.
- `analog[4..15]`: bytes 6..17 * (1/255), pressure. Needs >= 0x12 bytes.
- Stick roles: d-pad bits and the flick come from `analog[2..3]` (the
  movement stick). Standard DS2 order makes `analog[0..1]` right and
  `analog[2..3]` left (inferred). The header comment on `mode` 1 says
  "left stick" for `analog[0..1]`, so one label is wrong.
- Pressure order (inferred, standard report): right, left, up, down,
  triangle, circle, cross, square, L1, R1, L2, R2.
- `analog_prev`: copy of `analog` after mirror negation, then re-negated
  like the `_unmasked` masks.

### Mirror option

Flag byte `D_0015EEB4` = `D_0015EEB0 + 4` (`gCheatMirroredLevels`, cheat
flag 4): the mirrored-levels cheat, not a pad setting. When set,
`analog[0]`/`analog[2]` are negated and 0x8000/0x2000 swapped in
`held`/`raw_held`; the `_unmasked` copies and `analog_prev` undo it.
pad.h gives the US address `D_0015EDB4`.

### Stick history and flick detector

Each poll stores left-stick magnitude/angle in `hist_mag`/`hist_ang`
(rings of 30). If magnitude is now > 0.9:

1. Look back `scale_game_frames(4) - 1` polls (`func_001F98C0`;
   `src/game/space.c:1738`): stop at the first sample > 0.9; a sample
   < 0.25 before that is a flick.
2. Else, over `scale_game_frames(5) - 1` polls, a
   `FastDiffRots(old, angle)` above 0.9599311 rad (55 degrees) is a flick.

A flick ORs 0x10000 into `pressed`. Then `hist_btn[hist_idx] = pressed`,
`hist_idx` advances mod 30, `hist_count` saturates at 30.
`ResetGlobalStateFields` clears both.

### Key repeat

Only when `rep_rate != 0`. While `held` is nonzero and equals `prev_held`,
`rep_timer` counts down; at 0 (or wrap to 0xFF) `rep_timer = rep_rate` and
**`pressed = held`** (the whole mask). Any change of `held` reloads
`rep_timer = rep_delay`.

### Polling (`func_00217F68`)

| `profile_state` | Action |
|---|---|
| 0 | read profile (`func_00124DF0` -> `profile`; `unk1DC = 0x79` if first word is 0xFFFFFFFF) and actuator block (`func_00125218` -> `act`); go to 1, or 2 if the profile is longer than 4 bytes; `unk18C = 2` |
| 1 | read report (`func_00124D18`) into `func_002181F0`; count `unk18C` down. While nonzero, `pressed`/`released` stay 0 (first two polls give no edges) |
| 2 | clear input |

A device state other than 1 clears input and resets to 0.

## Addresses: PAL vs US

`FUN_Lxx_...` names and US addresses in header comments come from the
NTSC decomp. In this data region US is 0x100 lower. Always use PAL in code.

|---|---|---|
| pad | `D_0013C940` | `D_0013CA40` |
| hero | `D_0013F350` | `D_0013F450` |
| mirror flag | `D_0015EDB4` | `D_0015EEB4` |
